Реализованный стек v0.9

Выбор уже воплощён: Phaser 3.90.0, TypeScript 5.9.3, Vite 7.3.6, ws 8.22.0 и Swiper 14.3.0; точные зависимости закреплены в lockfile. Проверено на Node.js 22. Unity и чистый Canvas не используются.

  • Клиент собирает ввод и HTML-интерфейс; Phaser-сцена рисует состояние; буфер отрисовки интерполирует подтверждённые снимки с задержкой 100 мс без экстраполяции старой скорости; при нехватке пакетов удерживает последнее подтверждённое состояние. Локального предсказания на основе ввода пока нет.
  • Общая симуляция без DOM считает оба режима на сервере: шаг 30 Гц, снимки 15 Гц. Поле 1200×675 сохраняется целиком; CSS ограничивает боевой экран 800×450 и меню шириной 800 px. Телефон работает только в landscape.
  • Сервер обслуживает /socket, подбор, ботов, кампанию, награды и операции профиля. Все режимы требуют соединения. При разрыве сокета участие в дуэли завершается; клиент переподключается, кампания восстанавливается из контрольной точки. Первое обучение запускает локальную симуляцию без наград и отправки ввода в серверный матч; отдельного офлайн-режима нет.
  • Хранилище прототипа — атомарная замена data/profiles.json одним процессом. Обычные изменения сохраняются каждые 500 мс; покупки, исследования и обмены ждут записи. Параметры старых контрольных точек пересчитываются с сохранением доли HP; аккаунт хранит победы над боссами, три попытки, исследования и суммарный опыт отдельно от расходуемого XP. Для публикации нужны транзакционная БД, резервные копии и серверная проверка подписанного Player.
  • Адаптер Яндекса и проверка покупок подготовлены, подписанные чеки и повторные операции покрыты тестами. Проект в консоли не создан, реальный SDK/оплаты не проверены. Токен гостевого профиля сохраняется через облако; это ещё не проверенная сервером личность Яндекса.
  • Готовые ресурсы: пять утверждённых PNG-самолётов игрока, три самолёта карьеры, включая бомбардировщик, три босса, три корпуса ПВО, SVG-иконки и музыкальная MP3-петля. Винты, золотой след и стволы ПВО анимируются в Canvas; скалы рисуются по общему с сервером полигону. Старые SVG сохранены как архив. Генератор рисунков использует стандартный Python; генератор музыки требует FFmpeg. Для игры и сборки генераторы не нужны.

Дополнительные проверки: npm run balance, npm run campaign:playthrough и npm run campaign:audit. Отчёты до текущих изменений кампании: матрица 50181 сборки, полное бесплатное прохождение, отдельные боевые сценарии. Их хеши относятся к прежней ревизии и не подтверждают новые переходы и наведение; полный прогон ещё не повторялся. Платные конфигурации в матрице используют тестовые ресурсы, не реальные платежи. Текущая проверка фиксирует 266 тестов, сборку и браузерные сценарии.

Запуск: npm ci, затем npm run server и npm run dev. Сборка: npm run build; проверки: npm test (266/266 в текущей проверке). Клиент dist загружается отдельно от Node-сервера; для размещения указать публичный WSS-адрес в VITE_SERVER_URL. Переменные сервера задаются в окружении процесса; .env.example автоматически сервером не читается.

Почему этот вариант подходит

У нас небольшая 2D-аркада с прямой браузерной интеграцией, частыми правками управления, магазина и баланса. «Знамёна эпох» уже использует Phaser 3.90 и TypeScript; «Разгадай и узнай» — TypeScript и HTML/CSS. Переиспользование опыта SDK и сборки сокращает число новых задач.

Canvas — поверхность вывода, а не готовый движок. Писать на чистом CanvasRenderingContext2D можно, но тогда самостоятельно понадобятся сцены, камера, загрузчик, работа со спрайтами и вводом. Phaser закрывает эти задачи. Для базовой линии выбираем проверенный в соседнем проекте Phaser 3.90 с точной версией и lockfile; это не заявление о том, что Phaser 3 является самой новой веткой.

В Phaser 3 режим Phaser.AUTO выбирает WebGL и допускает переход к Canvas при отсутствии его поддержки. Визуальный дизайн поэтому не должен зависеть от обязательных шейдеров. Официальное описание рендереров Phaser 3.

Выбор: Phaser для сцены и анимации; собственная небольшая модель полёта на чистом TypeScript; HTML/CSS для меню; Vite для клиента; Node.js и защищённые WebSocket-соединения для дуэлей. Версии зафиксированы в package.json и package-lock.json.

Как разделить клиент и правила

HTML/CSS: интерфейс↔Phaser: сцена↔TypeScript: симуляция↔Сервер: матч и профиль
  • Общая симуляция: движение, урон, перегрев, модули и AI без DOM и Phaser. Фиксированный шаг, проверяемые входы, версия правил.
  • Сцена: камера, законченные мультяшные спрайты, полный набор подходящих эффектов действий, частицы, звук, интерполяция состояния и сбор ввода. Физика рендерера не определяет итог попадания в PvP.
  • Интерфейс: ангар, каталог, улучшения, задачи, очередь и результат. Реальные HTML-кнопки, локализация и безопасные области экрана.
  • Адаптер платформы: готовность игры, реклама, покупки, добровольная авторизация, время и жизненный цикл.
  • Сервер: очередь, матчи, безопасный профиль, журнал операций, награды и проверка платежей. Клиент не назначает себе валюту.
  • Данные: самолёты, золотые детали, модули по моделям, профильные навыки, модификаторы и 250 операций с ID и версией баланса. Семь типов миссий и геометрия воспроизводимо выбираются по номеру операции и вылета. Боссы стоят на 10/25/50 и далее каждые 25 до 250. Продаваемый модуль связан со стабильным ID, а не позицией в массиве.

В текущей кампании обычные вылеты остаются в фазе flight и продолжаются автоматически. При смене задачи сбрасываются её счётчики и восстанавливается здоровье; внутри операции также полностью восстанавливается форсаж. Позиция игрока, активная фаза и физические объекты мира сохраняются. Старые кольца и контейнеры получают retired: их можно подобрать, но они не увеличивают счётчик новой задачи. Прежняя контрольная точка sortie-reward при загрузке автоматически продолжает маршрут, без повторной награды. Остановка boss-intro сохраняет возможность зайти в ангар и предупреждает о смене управления. Переход к подготовке босса очищает обычный мир и создаёт арену; возвращение после босса создаёт следующую карту. Рендер и управление используют одну сцену и общий буфер интерполяции.

Контрольные точки сохраняют состояние кампании и уже полученные награды. Формирование группы, геометрия корпуса и полосы бомб вынесены в shared/bombers.ts; авторитетная симуляция и предупреждение в клиенте используют одинаковые позиции. Прицел следует за игроком до начала предупреждения, затем фиксируется. Модель и анимация бомбардировщика подключены к общей системе PNG-самолётов, отдельной логики рисования корпуса нет. Урок использует список действий по режиму: шесть для кампании, четыре для дуэли.

Совпадение языка не гарантирует побитовую детерминированность разных JS-сред. Сервер остаётся авторитетом; в v0.9 клиент интерполирует подтверждённые снимки без экстраполяции, но не предсказывает движение по локальному вводу. Для аркадного полёта предлагаем собственные простые столкновения и проверку пересечения пути снаряда, а не сложную физику жёстких тел.

Онлайн не появляется от выбора движка

Настоящей реактивной дуэли нужен постоянно доступный сервис матчей. План MVP: один развёртываемый backend, один регион до подтверждения спроса, HTTPS для профиля и платежей, WSS для ввода и состояния матча. Масштабирование и число регионов определяются реальными задержками и аудиторией.

Яндекс предоставляет асинхронные записи сессий, которыми можно воспроизводить действия других игроков. Для нашего боя, где противник реагирует на манёвр прямо сейчас, это не заменяет живой матч. Здесь оставляем настоящую онлайн-дуэль и бота после ожидания. Официальный асинхронный мультиплеер.

Unity Web также ограничен браузерной сетью: прямые TCP/UDP-сокеты и обычные сетевые классы .NET недоступны. Поэтому переход на Unity не устраняет необходимость транспорта и backend. Официальные ограничения Unity Web networking.

Хранение и доверие

Серебро, опыт, золото, покупки и награды хранит серверный профиль с журналом операций. Локальная копия — кэш и восстановление незавершённой сессии. Подпись покупки проверяется на сервере; повторная доставка одного токена не начисляет товар второй раз. Постоянные права на купленный контент восстанавливаются отдельно от расходуемого золота. Премиум ограничен 30 днями: сервер хранит точный expiresAt в чеке, продление добавляет срок к max(now, expiresAt), повтор не выдаёт новый месяц. Подтверждение расходуемого чека выполняется после долговечной записи.

Гость может играть без Яндекс ID: сервер создаёт гостевой профиль. Перенос в Яндекс ID выполняется однократно и без сложения двух кошельков; существующий прогресс нельзя незаметно перезаписать. Проверка платформенной идентичности и связь покупки с гостевым профилем — отдельный обязательный тест перед выпуском, а не доверие строке user ID от клиента.

Будущее улучшение: при недоступном backend добавить локальную тренировку; магазин, выдача экономики и онлайн временно недоступны, состояние объясняется в интерфейсе. Награды из недоверенной офлайн-копии не переносятся в платный кошелёк. Игра рассчитана на онлайн-площадку, а не на полное офлайн-прохождение.

Что измерить до наполнения

Это внутренние технические ориентиры, не требования Яндекса и не результаты замеров.

  • 60 FPS на выбранном среднем Android в бою; 30 FPS как нижняя граница облегчённого режима. Проверять также проход всех 250 уровней, все 11 переходов к боссам и возвраты, нагрев, накопление объектов и продолжение сохранения.
  • Стартовые ресурсы до первого боя — цель ≤5 МБ переданных сжатых данных; первая управляемая сцена — цель ≤5 секунд при чистом кэше и тестовой сети 10 Мбит/с, RTT 80 мс. Условия и устройство записывать с замером.
  • Серверный шаг 30 Гц, клиентский рендер до 60 Гц, снимки состояния 10–15 Гц — начальные настройки, которые проверяются под задержками 50/100/150/250 мс и потерями пакетов.
  • При RTT выше 200 мс показывать качество связи; до подтверждения приемлемых матчей не смешивать удалённые регионы только ради меньшего числа ботов.
  • Измерять пиковую память, размер атласов, долю долгих кадров, объём трафика и стоимость на 1000 завершённых дуэлей. Денежный бюджет сервера определяется владельцем после измерения.

Матрица проверки: Chrome/Яндекс Браузер на Android, Safari на iPhone, Chrome/Edge на ПК; маленькое горизонтальное окно, поворот устройства, iframe Яндекса, плохая сеть и потеря фокуса. Canvas fallback не считается проверенным, пока сцена реально не запущена в этом режиме.

Что полезно перенести из соседних игр

  • Паттерн адаптера SDK, вызовы готовности и разметки геймплея, отдельные причины паузы и выдачу rewarded только при подтверждённом просмотре.
  • Паттерн упаковки: корневой index.html, относительные ассеты, проверка состава архива и отдельное тестирование в черновике.
  • Обработку конфликтов сохранений и резервных копий как исходный опыт, но не клиентский кошелёк для платной игры.
  • Проверку горизонтального телефона и низкого экрана результатов. Цвета, интерфейс и баланс этой игры создаются отдельно.

Исходные соседние проекты не изменены. Прямой перенос кода сейчас не выполнялся. Адаптер, экономика и интерфейс реализованы отдельно для этого проекта; исходники соседних игр остаются только референсами.

Когда Unity станет лучшим выбором

Unity имеет смысл, если появится значимый план нативного выпуска, команда работает в C#, нужен развитый редактор сложных уровней или уже есть проверенный Unity-проект с полётом и платформенной интеграцией. В таком случае отдельная тестовая Web-сборка на реальном телефоне должна пройти проверку загрузки, памяти, покупки и сетевого боя до окончательного выбора.

Актуальная документация Unity 6.3 перечисляет мобильную поддержку, в том числе Safari на iOS и Chrome на Android. Поэтому аргумент «Unity вообще не работает на мобильном вебе» здесь неверен. Поддержка браузера сама по себе не гарантирует, что наша сборка уложится в требуемую производительность. Совместимость Unity 6.3.

Практическое решение для текущего объёма: продолжать на реализованном Phaser + TypeScript. Пересматривать его после прототипа только при измеренной проблеме, которую нельзя разумно устранить, или при изменении целей проекта.
